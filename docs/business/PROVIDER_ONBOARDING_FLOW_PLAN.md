# 服务商入驻流程产品化计划

## 1. 目标

把当前“服务商能力未开通”的门禁页，升级为完整、可解释、可恢复的服务商入驻流程。

产品侧只保留两个入口：

- `我要吊运`：客户下单、选方案、支付边界、订单跟踪。
- `我要接单`：服务商入驻、接单、报价、履约、结算。

内部兼容字段 `owner / pilot / client` 暂不迁移，但用户可见表达统一为：

- 客户
- 服务商

## 2. 当前状态

已经完成：

- 小程序和 App 均有 `customer / provider` 模式。
- 新账号或客户号可以进入 `我要接单`，不会被静默切回 `我要吊运`。
- 未审核服务商不能进入正式工作台、服务、报价、钱包、提现等经营页面。
- 后端已拦截未审核账号直打正式服务商接口：
  - `/owner/workbench`
  - `/owner/supplies`
  - `/owner/quotes`
  - `/owner/pilot-bindings`
- P0 主链路已跑通：客户发布需求 -> 服务商报价 -> 客户选择方案 -> 服务商开始履约 -> 履约推进 -> 结算。

当前不足：

- 入驻流程只是散落在“服务商资料 / 设备与资质 / 履约资质 / 实名认证”几个入口中。
- 没有统一的入驻首页、进度条、拒绝原因、重新提交路径。
- 设备资质和履约资质的关系还不够直观。
- 管理端审核能力可用，但前端没有把审核状态组织成一个清晰流程。

## 3. 参考业务逻辑

参考货拉拉类平台，不照搬代码，只取流程逻辑：

1. 任何新用户都可以点击 `我要接单`。
2. 点击后不是直接接单，而是进入服务商入驻。
3. 入驻通过后台审核后，才开放正式接单、报价、履约、结算。
4. 服务商能力可以分层：
   - 设备服务能力：有可上架无人机和资质，可以报价、上架服务。
   - 履约能力：服务商主体具备履约资质，可以推进订单履约。
   - 综合能力：同时具备设备和履约条件，可以直接自履约。
5. 审核中、被拒、暂停都必须有明确解释和下一步动作。

## 4. 服务商状态机

统一状态来自 `role_summary.provider`：

| 状态 | 含义 | 用户能做什么 |
|------|------|--------------|
| `none` | 从未开始入驻 | 进入入驻首页，选择开通设备能力或执行能力 |
| `pending_review` | 已提交资料，等待审核 | 查看入驻进度、补充非锁定资料，不能正式经营 |
| `approved` | 服务商能力审核通过 | 进入正式工作台，开放报价、接单和履约 |
| `rejected` | 审核被拒 | 查看拒绝原因，修改资料后重新提交 |
| `suspended` | 账号或服务商能力暂停 | 查看暂停原因，不能经营，联系平台或补材料 |

能力子状态：

| 能力 | 字段 | 通过后的权限 |
|------|------|--------------|
| 设备服务能力 | `asset_status=approved` | 报价、上架服务、查看经营财务 |
| 履约能力 | `executor_status=approved` 或服务商主体履约通过 | 履约推进、查看服务收入 |
| 综合能力 | 设备和履约条件均满足 | 可直接自履约 |

## 5. 小程序页面规划

### 5.1 新增统一入驻首页

建议新增：

```text
mini-program/src/pages/provider/onboarding/index.tsx
```

页面职责：

- 显示当前服务商总状态。
- 显示两条能力路径：
  - 设备服务商
  - 履约资质
- 显示每条路径的资料完成度、审核状态、下一步动作。
- 不展示任何经营数据。

页面结构：

1. 顶部状态卡
   - 未开通：`开始服务商入驻`
   - 审核中：`服务商资质审核中`
   - 被拒：`资料需修改`
   - 已通过：`服务商能力已开通`

2. 能力路径卡
   - 设备服务能力
     - 服务商资料
     - 无人机设备
     - UOM / 保险 / 适航
     - 服务城市与联系方式
   - 履约能力
     - 履约人员/服务商资料
     - CAAC / 健康 / 无犯罪等资料
     - 服务城市与接单状态

3. 基础资料卡
   - 实名认证
   - 手机号
   - 账号状态

4. 底部主动作
   - `继续完善资料`
   - `查看审核进度`
   - `重新提交`
   - `进入工作台`

### 5.2 改造现有页面

| 当前页面 | 处理方式 | 说明 |
|----------|----------|------|
| `pages/home/ProviderWorkbench.tsx` | 保留 | 未通过时跳统一入驻首页或展示入驻卡 |
| `pages/profile/owner/index.tsx` | 改为“服务商资料与设备能力” | 不再承担整个入驻首页 |
| `pages/profile/drones/index.tsx` | 保留 | 设备管理和资质入口 |
| `pages/pilot/register/index.tsx` | 改为“服务商履约资质” | 文案全部服务商化 |
| `pages/verification/index` | 保留 | 只是基础实名，不等于服务商入驻完成 |
| `ProviderAccessNotice` | 保留 | 所有正式经营页面直达时统一拦截，并跳入驻首页 |

### 5.3 入口行为

| 用户动作 | 预期结果 |
|----------|----------|
| 新用户点 `我要接单` | 进入服务商入驻首页 |
| 客户号点 `我要接单` | 进入服务商入驻首页，不切回客户首页 |
| 未审核账号点工作台 | 显示入驻进度，不展示经营数据 |
| 未审核账号直达报价/服务/钱包 | 显示 `ProviderAccessNotice`，主按钮进入入驻首页 |
| 已审核服务商进入 | 进入工作台，可报价、接单、管理服务和推进履约 |

## 6. App 对齐规则

App 不重新设计业务模型，直接复用小程序状态机和接口。

允许差异：

- 原生导航栏
- 安全区
- 页面交互控件形态

不允许差异：

- 同账号同入口看到不同服务商状态。
- 小程序能拦截、App 能绕过。
- App 继续展示设计稿静态服务商、金额、订单号。

App 后续对应新增或改造：

```text
mobile/src/screens/provider/ProviderOnboardingScreen.tsx
```

并让以下页面 gate 的主按钮统一跳入驻页：

- `OwnerProfileScreen`
- `PublishOfferScreen`
- `MyOffersScreen`
- `MyQuotesScreen`
- `OwnerPilotBindingsScreen`
- `WalletScreen`
- `WithdrawalScreen`
- `DemandQuoteComposeScreen`

## 8. 管理端最小需求

当前管理端不作为 UI 重构重点，但必须能支撑审核闭环。

最小闭环：

- 设备资料审核：通过 / 驳回，驳回原因回传。
- 保险审核：通过 / 驳回，驳回原因回传。
- 适航 / UOM 审核：通过 / 驳回。
- 履约资质审核：通过 / 驳回。
- 服务商暂停 / 恢复。

前端必须能显示：

- 正在审核哪个能力。
- 哪个资料被拒。
- 被拒原因。
- 修改后重新提交。

## 9. 分阶段实施

### P0：统一入驻首页

目标：解决用户不知道为什么不能接单、下一步该做什么。

任务：

1. 新增小程序 `provider/onboarding` 页面。
2. `ProviderWorkbench` 未通过时跳转或嵌入入驻首页。
3. `ProviderAccessNotice` 主按钮统一跳入驻首页。
4. `profile/owner` 只负责服务商资料，不再承担全局入驻解释。
5. 构建和 P0 smoke 通过。

验收：

- `13800000004` 进 `我要接单` 后看到统一入驻首页。
- 点击“继续完善资料”不会跳回客户模式。
- 未审核账号直达经营页面都回入驻首页。

### P1：资料状态和拒绝原因

目标：用户能知道卡在哪里。

任务：

1. 聚合设备、保险、适航、UOM、履约资质状态。
2. 页面展示 `待完善 / 审核中 / 已通过 / 已驳回`。
3. 驳回原因可见。
4. 每个步骤点进去对应资料页。

验收：

- 被拒设备资料能看到原因。
- 修改后重新提交，状态回到审核中。
- 已通过项不可误导为还要重复提交。

### P2：App 对齐

目标：App 与小程序同账号同状态。

任务：

1. 新增 App `ProviderOnboardingScreen`。
2. 所有 App provider gate 主按钮跳入驻页。
3. 文案、状态、下一步动作与小程序一致。
4. App 不展示设计稿假数据。

验收：

- 同一账号小程序和 App 看到同一服务商状态。
- 未审核账号在 App 也无法绕过 gate。

### P3：专用后端摘要接口

目标：减少前端拼状态，提高稳定性。

任务：

1. 新增 `/api/v2/provider/onboarding`。
2. 后端统一计算入驻步骤、状态、拒绝原因。
3. 小程序和 App 改用该接口。
4. 补服务层测试。

验收：

- 空资料、审核中、通过、驳回、暂停都有测试覆盖。
- 前端不再各自散拼入驻状态。
