# 服务商自履约主流程收敛计划

## 目标

小程序 `我要接单` P0 只保留服务商主体接单：

- 客户发布需求或选择服务商。
- 服务商报价 / 确认接单。
- 客户完成合同和支付边界。
- 服务商直接开始履约、推进准备 / 吊运 / 送达。
- 客户确认完成并生成结算。

旧的 `dispatch_tasks`、绑定人员、候选执行池继续作为后端兼容能力保留，但不再作为小程序 P0 主流程展示。

## 本轮代码约束

- 用户可见文案统一为 `服务商接单`、`开始履约`、`确认送达`。
- 小程序主入口不再展示 `安排执行人员`、`待我确认派单`、`协作执行人员`。
- 服务商工作台只聚合真实需求、待接单订单、待开始履约订单和财务数据。
- 履约安排页遇到 `pending_dispatch` 时调用自履约兼容接口，让订单进入 `assigned`。
- 后端仍保留旧派单接口和表结构，避免破坏既有数据和管理端兼容。

## 后续边界

- 管理端可以继续看到旧派单数据，但不作为当前产品主流程。
- App 端后续对齐小程序冻结后的状态和文案，不单独设计第三端。
- 合同、结算字段里的 `pilot/owner` 内部命名暂不迁移；展示层统一解释为服务商履约和设备服务。

## 验收点

- 客户账号进入 `我要接单` 只能看到入驻 / 审核 gate。
- 服务商账号进入 `我要接单` 能看到真实可接需求和正式工作台。
- 服务商确认订单并支付后，订单不要求再找另一个账号接单。
- 服务商可在履约页推进 `preparing -> in_transit -> delivered`。
- 客户确认完成后能生成结算。
- 小程序主流程不出现 `飞手`、`机主`、`执行人员接单`、`待确认派单` 等三端表达。
