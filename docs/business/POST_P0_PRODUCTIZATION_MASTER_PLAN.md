# 主链路跑通后的产品化总计划

## 0. 当前结论

当前已经跑通的是最小主链路：

```text
客户发布需求 -> 服务商报价 -> 客户选择方案 -> 合同/支付边界 -> 服务商开始履约 -> 服务商推进送达 -> 客户确认完成 -> 结算入账
```

这只证明系统具备基础闭环能力，还不能说明产品已经可用。下一步不应该马上继续扩页面，也不应该跳去 Web，而是要把小程序这条真实链路做成稳定、可解释、可验收的产品形态。

## 1. 大纲

### 第一阶段：小程序 P0 产品冻结

目标：让 `我要吊运` 和 `我要接单` 两个入口在小程序里不串模式、不露旧入口、不展示假数据。

重点：

- 清理所有主路径里的 `机主 / 飞手 / 执行人员接单 / 派给别人确认` 表达。
- 旧 `dispatch_tasks` 只保留兼容，不作为小程序主流程。
- 01-08 已设计页面必须使用真实数据、空态、失败态。
- 生产构建不允许静默 mock 成功。

### 第二阶段：服务商入驻产品化

目标：新用户点击 `我要接单` 后，知道自己缺什么、为什么不能接单、下一步补什么资料。

重点：

- 统一服务商入驻首页。
- 设备资质、保险、适航、UOM、基础身份状态聚合展示。
- 审核中、被拒、暂停、通过都要有明确文案和下一步动作。
- 未审核账号直达正式经营页必须统一 gate。

### 第三阶段：履约和订单体验补齐

目标：主链路从“接口能跑”升级为“用户能理解并完成”。

重点：

- 服务商履约页补齐开始履约、现场复核、吊运中、确认送达的状态和按钮。
- 客户订单详情补齐支付前、履约中、待确认、已完成、售后的状态。
- 异常、取消、退款、售后入口不再是散点页面。
- 结算明细能解释平台服务费、服务商收入、提现边界。

### 第四阶段：App 对齐小程序

目标：App 不是重新做一套逻辑，而是复用小程序冻结后的业务规则和接口状态。

重点：

- App 01-08 对齐小程序状态、文案、空态、失败态。
- 只允许因为原生导航、安全区、微信胶囊差异带来 UI 差异。
- App 不再展示设计图假公司、假订单号、假金额。

### 第五阶段：非主链路批量收口

目标：清理历史页面和辅助能力，让它们不破坏双入口模型。

重点：

- 消息、合同、评价、售后、钱包、提现、保险、空域、设备资料。
- 旧 cargo、owner、pilot、client 入口重定向或降级为内部兼容页。
- 管理端只补审核和运营必需能力，不做 UI 重构优先项。

## 2. 执行计划

### P1：小程序 P0 产品冻结

#### P1-1 路由和入口冻结

交付：

- 更新小程序路由矩阵，将旧 `dispatch/list`、`dispatch/detail`、`dispatch/create` 标为兼容/延后，不再是 P0 主链路。
- `provider` tab 只进入工作台、接单需求、消息、我的。
- `查看账号资料`、`我的`、返回按钮都不能把 `provider` 模式切回 `customer`。

验收：

- 客户号进入 `我要接单` 后，不能绕过 gate。
- 服务商号进入 `我要接单` 后，工作台不显示 `待我确认派单`。
- `rg` 主路径不出现 `飞手端 / 机主端 / 执行人员接单 / 待确认派单`。

#### P1-2 真实数据和空态冻结

交付：

- 01-08 页面逐页检查数据来源。
- 所有设计图静态公司名、静态订单号、静态金额只允许作为开发占位，不允许生产展示。
- 接口失败显示错误态；后端无数据显示空态。

验收：

- `npm run build:weapp`
- `npm run build:weapp:prod`
- 后端空数据时，客户和服务商页面没有假卡片。

#### P1-3 主链路接口回归

交付：

- `mini_program_p0_acceptance.sh` 固化为两账号验收：客户 + 服务商。
- 报告记录 `demand_id / quote_id / order_id / settlement_id`。

验收：

- 客户发布需求。
- 服务商报价。
- 客户选方案并支付。
- 服务商自己推进履约。
- 客户确认完成。
- 结算入账。

### P2：服务商入驻产品化

#### P2-1 入驻首页

交付：

- `pages/provider/onboarding/index` 成为 `我要接单` 未通过时的唯一解释页。
- 显示服务商总状态、设备资质状态、审核状态、下一步动作。

验收：

- 新用户可进入入驻页。
- 被拒、审核中、已通过状态展示不同文案。
- 不能把实名认证误认为服务商入驻完成。

#### P2-2 资料闭环

交付：

- 服务商资料、设备资料、保险资料、适航/UOM 状态形成可回到入驻页的闭环。
- 资料提交后可看到审核中。
- 审核拒绝能看到原因并重新提交。

验收：

- 未审核不能报价。
- 审核通过后能进入工作台。
- 资料被拒时不能展示正式经营数据。

### P3：订单和履约体验补齐

#### P3-1 服务商履约页

交付：

- `确认接单`、`开始履约`、`现场复核`、`开始吊运`、`确认送达` 的按钮状态明确。
- 禁止越级推进不合法状态。
- 现场复核、保险、空域状态真实读取。

验收：

- 服务商能从订单详情进入履约页。
- 每个状态只能看到当前可操作按钮。
- 失败时显示后端错误，不假成功。

#### P3-2 客户订单页

交付：

- 客户能理解当前处于：待服务商确认、待支付、服务商已接单、履约中、待确认、已完成。
- 支付边界继续使用 mock，但生产文案标明真实回调暂不可用。
- 售后、评价、合同入口按状态显示。

验收：

- 同一订单客户侧和服务商侧状态一致。
- 已完成订单能评价。
- 退款/售后入口不误导成已实现真实支付回调。

#### P3-3 财务和提现

交付：

- 结算明细解释客户实付、平台服务费、服务商收入。
- 钱包、提现、提现记录读取真实接口。
- 无资质或无数据时不展示假收入。

验收：

- 已完成订单生成结算。
- 服务商钱包能看到入账。
- 提现页能区分可提现、冻结、无余额。

### P4：App 01-08 对齐

交付：

- App 复用小程序已冻结业务状态和文案。
- App 01-08 不依赖静态设计图数据。
- App 服务商入口不出现第三端表达。

验收：

- `npx tsc --noEmit --pretty false`
- `npx eslint src --max-warnings=999`
- 同一账号同一订单，小程序和 App 状态一致。

### P5：剩余页面批量收口

交付：

- 历史 legacy 页面按 `KEEP / REWIRE / REDIRECT / DEFER` 清理。
- 旧 `cargo / owner / pilot / client` 用户入口不再进入主导航。
- 管理端只补审核必要功能。

验收：

- 用户主路径只有 `我要吊运 / 我要接单`。
- 旧链接不会绕过权限。
- 文案不再让用户误以为有三个端。

## 3. 当前立即执行顺序

### 当前 Sprint 只做 P1

1. 修正旧路由矩阵和旧计划文档，把服务商自履约设为唯一 P0 主流程。
2. 扫描小程序主路径残留的 `飞手 / 机主 / 执行人员 / 派单` 展示文案。
3. 逐页处理 01-08 的真实数据、空态、失败态。
4. 跑 `mini_program_p0_acceptance.sh`、`build:weapp`、`build:weapp:prod`。

### 不做

- 暂不继续 Web UI。
- 暂不做 App 01-08，等小程序 P1 冻结。
- 暂不做微信/支付宝真实回调。
- 暂不删除数据库 `owner/pilot/dispatch_tasks` 兼容字段。

## 4. 完成定义

小程序 P1 完成时，必须满足：

- 客户和服务商两个入口不会串。
- 未审核服务商不能看到经营数据。
- 已审核服务商能报价、接单、自履约、结算。
- 生产构建无静默假数据。
- 小程序主路径不再出现三端模型文案。
- 接口级验收和小程序构建全部通过。
